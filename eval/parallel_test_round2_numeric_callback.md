# round2 (`checkpoints/lilas.pt`) 並列テスト: 数字・日付callbackの失敗の特性調査

日時: 2026-09-10
対象チェックポイント: `checkpoints/lilas.pt` (tag: round2)
テスト方法: `lilas.chat.generate_reply` を直接呼び出す複数ターン会話(履歴を手動で積み上げ)。
サンプリングパラメータはチェックポイント同梱のデフォルト値(temperature=0.8, top_k=40, top_p=0.9,
repetition_penalty=1.15)。乱数シード固定はしていないため、個々の出力は実行毎に多少変動しうるが、
以下に示す「パターン」自体(訓練済み値への置換・テンプレート漏れ・無回答化)は複数の独立した会話で
繰り返し確認された。

## 0. 事前調査: 何が訓練されているか

`scripts/generate_longcontext_data.py` のトピック27・29・30・31(修理仕上がり時期、荷物到着日、
サプライズ実行日、価格交渉)を確認した。重要な点:

- 各トピックは `slots` に**4パターン前後の固定の具体値**(例: トピック27の `repair_time` は
  `3日後 / 1週間後 / 来月頭 / 明日` の4つだけ)しか持たない (`slot_variants` 辞書, L682-800)。
- `callback_a`(呼び戻しの答え)は3パターン用意されているが、いずれも `{repair_time}` 等のスロット値を
  **テンプレートにそのまま埋め込む**形式で、「文脈から値を読み取ってコピーする」という汎化可能な
  スキルではなく、「トピック識別 → 対応する固定値をテンプレートに当てはめる」形の教師信号になっている。
- 価格交渉(トピック31)のみ真の多桁の数字(`50000/40000`, `30000/25000`, `20000/15000`)を使い、
  他の3トピックは「3日後」「明日」のような相対的な日付表現(数字+助数詞)を使っている。
- 各バリエーションは2〜3回複製されるのみで(L806-808)、他の一般名詞トピック(24種類)に比べて
  この4トピックの絶対件数はコーパス全体の中でごく少数。

この設計自体が、後述する「トピック識別→訓練済み固定値のうち1つを返す」という挙動を助長しうる
構造であることに留意。

## 2. 発見したパターン(なぜ失敗するか)

### パターンA: 「訓練済みの固定値への置換」(最も重要な発見)
新しい値を与えても、**訓練データに含まれる別の固定値**をもっともらしく返すケースが繰り返し観測された:

- C1-1: 実際は「5日後」→ 出力は「明日」(topic27の訓練済み4値の1つ)
- C1-4: 実際は「来月の結婚式」→ 出力は「来月の誕生日」(topic30の訓練済み4値の1つ)
- C2-3, R2: 実際は「1週間後」「4日後」→ どちらも「明日」に置換
- P1: 実際は「35000円」→ 出力は「500円から**40000円**」(40000はtopic31の訓練済み値)

「明日」は複数トピックにまたがってコーパス全体で頻出する語(修理の訓練値の1つであると同時に、
他トピックの相対日付表現としても頻繁に登場)であり、修理トピックの呼び戻し時のデフォルト応答に
なっている様子が繰り返し確認できた。これは**文脈から値をコピーする機構ではなく、「この話題形なら
だいたいこの値」という頻度ベースの連想を学習している**ことを強く示唆する。

### パターンB: 無回答・テンプレート漏れ(最多)
数字を一切出さず、話題自体は認識しつつ(「修理のお話でしたね」等)値を埋めずに終わる、
あるいは全く無関係な定型文・他トピックの定型文が漏れ出す、または質問文をほぼオウム返しする
(C1-3)。件数として最も多いパターン。

### パターンC: 完全な迷子(未訓練の型で顕著)
C4の会議時刻・年齢・値段(雑談扱い)・部屋番号では、数字どころか話題自体を見失い、
全く無関係な話題に飛ぶケースが複数あった(例: 甥の年齢の質問に対してカフェの話を返す)。

### パターンD: 同一ターン内(距離ゼロ、指示形式)でも数字生成は不安定
「さっき言った金額を復唱して」のような同一発話内(記憶を跨がない)テストでも、
存在しない数字を自信満々に生成する(C6-1: 3000円→「約270円です」)、無関係な定型文で
はぐらかす(C6-2)、コードブロックのような破綻した出力になる(C6-3)、という3通りの失敗が出た。
ただし、この種の「〜を復唱して」という指示追従的な発話自体が訓練データの会話形式(テンプレート
雑談)には存在しない全く未知のパターンであるため、この結果は「数字コピー能力の限界」と
「指示追従自体が未訓練」という2つの要因が混ざっている可能性がある点は留意。

### 名前との比較(対照実験)
「名前呼び戻しは頑健」という他エージェントの報告を確認するため、**訓練データの4つの固定名
(モモ/ハチ/ユキ/コロ等)ではなく未訓練の新規名**(ポチ/ソラ/ミケ)で、かつ名前を問題文に
含まない訓練形式そのままのcallback_qを使って再検証した。

結果: 距離1(N1)・距離4(N2)ではいずれも名前が脱落し(「猫ちゃんのお話でしたね」と一般名詞化)、
**距離ゼロ(N3)でのみ正解**。C3-CTRL(距離4、犬の名前「タロ」)も同様に脱落。

→ つまり「名前は頑健」という評価は、**訓練済みの固定名(モモ等)を使った場合**、あるいは
呼び戻し質問自体に名前が再掲される言い回しを使った場合の結果である可能性が高い。純粋に
未訓練の新規値というだけであれば、名前もこのモデルでは距離が伸びると同様に脆い。

ただし重要な非対称性がある: **距離ゼロという最も簡単な条件では、名前(N3)は成功するが数字
(C2-3, R1, R2はいずれも距離0〜1で失敗)は成功しない**。これは「新規の値全般が苦手」という
一般論だけでは説明しきれず、数字固有の追加ハンディキャップが存在することを示している。

## 3. トークナイザ分析(数字固有のハンディキャップの原因候補)

`lilas/tokenizer.py` はバイトレベルBPEで、`[a-zA-Z0-9]+` をひとまとまりの事前分割単位として
扱う。実際にいくつかの数字・名前をエンコードして比較した:

```
'45000'  -> 2 tokens: ['45', '000']
'35000'  -> 2 tokens: ['35', '000']
'50000'  -> 2 tokens: ['500', '00']     # 訓練データに存在する値
'40000'  -> 2 tokens: ['400', '00']     # 訓練データに存在する値
'3000'   -> 1 token : ['3000']          # 訓練データに存在する値(まるごと1トークン)
'5000'   -> 1 token : ['5000']          # 訓練データに存在する値(まるごと1トークン)
'4000'   -> 1 token : ['4000']          # 訓練データに存在する値(まるごと1トークン)
'8000'   -> 1 token : ['8000']          # 訓練データに存在する値(まるごと1トークン)
'6000'   -> 2 tokens: ['6', '000']      # 訓練データに存在しない値
'503'    -> 2 tokens: ['50', '3']
'ポチ'    -> 2 tokens: ['ポ', 'チ']
'ソラ'    -> 2 tokens: ['ソ', 'ラ']
'ハチ'    -> 1 token : ['ハチ']          # 訓練データに存在する名前(まるごと1トークン)
```

**これは看過できない発見**: コーパス中に高頻度で登場した具体的な数字(3000, 5000, 4000, 8000,
50000, 40000 など)は、BPEマージの結果**それぞれ独自の分割境界(場合によっては数字列まるごと1
トークン)を獲得している**。一方、同程度の桁数でも訓練データに登場しなかった数字(6000, 45000,
35000)は、たまたま残った汎用的な境界(2桁+3桁のゼロ、など)で分割される。つまりこのトークナイザは
「万の位・千の位…という位取りに基づく一貫した数字表現」を持っておらず、**数字ごとに全く異なる
トークン列**になる。

これは名前の場合(「ポチ」も「モモ」も同じ2文字カタカナ分割ルールに従うか、頻度が高ければ
まるごと1トークン化されるだけで、どちらにせよトークン境界の「形」自体は数字ほど不規則ではない)
と比べて、数字の方がトークン列の構造が個体ごとにバラバラになりやすい。P1で「45000」が
「500円」に化けた(500は50000の一部としてまるごと1トークンで訓練データに存在する)のは、
この不規則なトークン境界と、モデルが特定の数字トークン列を「トピックに紐づく答えの断片」として
まるごと覚えてしまっている、という2つの問題が組み合わさった結果と解釈するのが最も自然である。

## 4. 結論: これは何の問題か

**訓練データの量の問題ではなく、(1) このタスクに対する訓練データの設計そのものの限界、
および (2) 数字のトークナイズが位取りで一貫していないという構造的な問題、の組み合わせである。
同じ種類のテンプレート生成データをさらに増やしても、根本的な改善は見込みにくい。**

根拠:

1. **完全一致(暗記)は距離に関わらず成功し、1文字でも新しい値は距離ゼロでも失敗する。**
   C3-1・C3-3(距離4・3、だが値が訓練データと完全一致)は正解。一方C2-3・R1・R2(距離0〜1だが
   値が新規)はいずれも失敗。つまり失敗の主要因は「遠さ」ではなく「見たことのない具体的な値
   かどうか」である。これは注意機構が長距離で弱まる問題ではなく、**そもそも文脈から値を
   コピーするという操作自体を獲得していない**ことを意味する。

2. **失敗時、多くのケースで訓練データ中の別の固定値に「もっともらしく」置換される**
   (パターンA)。これは「トピックの型を認識 → その型に紐づく学習済みテンプレート(と、
   その中の1つの固定値)を復元する」という、事実上の連想記憶・ルックアップテーブル的な
   挙動であり、genuine な in-context コピー(推論時にプロンプト中の任意の値を参照して
   再生成する能力、いわゆるinduction head的な機構)とは根本的に別のスキルである。
   round2の学習データ(topics 27/29/30/31)は「テンプレート文+4パターン程度の固定値」という
   設計であるため、たとえ複製回数を増やしても、モデルが学習できるのは「このトピックには
   だいたいこの数種類の値のどれかが対応する」という分布であって、「任意の値をその場でコピーする」
   という汎化可能なアルゴリズムではない。これは量ではなく**データの形の限界**。

3. **トークナイザが数字の位取りを一貫して表現できていない。** 訓練データに含まれる具体的な
   数字は1トークンやトピック固有の分割になり、含まれない数字は別の分割になる。この状態では、
   モデルが「数字列をそのままコピーする」という位置非依存の一般規則を学習するのは、通常の
   固定語彙BPEよりもさらに難しい。これは学習量では解決できない**トークナイザ設計上の制約**であり、
   数字を桁ごとに分割する、あるいは数字を独立した特別な符号化にする等のトークナイザ側の変更が
   本質的な対策になりうる。

4. **名前(固有名詞)でも、未訓練の新規名は同様に距離が伸びると脆い**(N1, N2, C3-CTRL)ことから、
   「名前は得意・数字は苦手」という単純な二分法ではなく、根本には「訓練データにない新規の
   スロット値全般をコピーする能力が乏しい」というより一般的な限界がある。ただし距離ゼロという
   最も簡単な条件でも数字だけは失敗し続けた(C2-3, R1, R2, C6-1〜3)のに対し名前は距離ゼロで
   成功した(N3)。この差は上記3のトークナイズの不規則性で最も自然に説明できる。

**まとめ:** 「訓練データにこのパターンを追加したのに直らなかった」のは、追加された訓練データが
「文脈から値をコピーする」という汎化可能なスキルではなく、「トピックの型と少数の固定値の対応」
という記憶を教える形になっていたため。さらに数字は、名前や地名などの固有名詞よりもトークン化が
不規則であるため、コピー元とコピー先で同じトークン列にすらならないことがあり、記憶に頼る戦略との
相性がさらに悪い。したがって、追加で有効そうな対策の優先順位は:
(a) トークナイザを数字専用に桁単位で一貫分割させる(またはBPEの数字マージを禁止する)、
(b) 「任意の数字をn ターン後にそのままコピーして答える」というコピー操作自体を明示的に
大量・多様な数値で訓練する(固定パターンの穴埋めではなく、真にランダムな数字を都度生成した
コピー専用データ)、
(c) 上記なしに同種のテンプレートデータの複製回数だけを増やす対策は、既にround2で試されており
効果が薄いことが本調査で確認できた。
