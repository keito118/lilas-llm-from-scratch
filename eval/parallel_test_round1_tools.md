# ツールトリガーのストレステスト結果 (round1)

対象: `lilas/calculator.py` (`try_calculate`, `_try_generic_expr`) と
`lilas/tools.py` (`try_datetime`, `try_holiday`, `try_weather`, `try_knowledge`,
`_extract_search_query`, `_looks_like_question`, `_SELF_REFERENCE_WORDS`)。

すべて **直接関数呼び出し**でテスト(ネットワーク不要な部分はオフラインで確認、
天気/祝日/Wikipediaは代表例のみ実際にAPIを叩いて動作確認済み)。
`generate_reply()`は今回対象外(他テスターがモデル品質側をカバーしているため、
トリガー分岐そのものの検証に絞った)。

呼び出し順序の確認: `chat.py`は`try_calculate()`を**最初に**呼び、Noneが
返った場合のみ`try_tools()`(datetime→holiday→weather→knowledgeの優先順)を呼ぶ。
つまり**1ターンにつき1つの事実しか注入されない**設計であることをまず確認した。
これが後述のバグの多くの根本原因になっている。

## 1. 電卓 (`calculator.py`) の誤爆・誤答

### 1-A. 日付・電話番号・郵便番号・時間帯・話数などの「N-M」表記を減算と誤認する

`_GENERIC_EXPR`の`-`(引く)演算子は、`\d[\d,]*\s*-\s*\d[\d,]*`という非常に緩い
パターンで、文脈を一切見ずに数字列の間の「-」を減算とみなす。日付・電話番号・
郵便番号・時間範囲・話数・日数の範囲表現がすべて誤爆する。

| 入力 | `try_calculate()`の返り値 | 問題 |
|---|---|---|
| `2026-09-10ですか?` | `2,026 - 9 = 2,017です。` | 日付を減算と誤読。**日付質問が`try_datetime`に届く前に電卓が横取りする**(呼び出し順序のため) |
| `TEL:090-1234-5678です` | `90 - 1,234 = -1,144です。` | 電話番号を減算と誤読。負の数という明らかに不自然な「答え」を自信満々に返す |
| `郵便番号163-8001です` | `163 - 8,001 = -7,838です。` | 郵便番号を減算と誤読 |
| `午前10-11時に会議です` | `10 - 11 = -1です。` | 時間帯表記を減算と誤読 |
| `第4-5話を見た` | `4 - 5 = -1です。` | 話数の範囲を減算と誤読 |
| `2-3日で届きます` | `2 - 3 = -1です。` | 日数の範囲を減算と誤読 |
| `5-3=2ですよね?` | `5 - 3 = 2です。` | 既に正しい式の確認文にまで反応(実害は小さいが、無用な割り込み) |
| `身長は170-160=10cmくらいの差です` | `170 - 160 = 10です。` | 同上、実害小さい |

**重大度: 高**。特に日付(`2026-09-10`のような表記)や電話番号・郵便番号は
日常会話で頻出し、負の数を「答え」として自信満々に返すのは会話を大きく破壊する。
`try_calculate`が`try_tools`より先に呼ばれるため、日付を尋ねる文に別の数字の
羅列(電話番号や日付そのもの)が入っていると、**正しいはずの`try_datetime`が
一生呼ばれない**。

**修正案**: `-`演算子だけ、前後が「YYYY-MM-DD」「電話番号らしい桁数(3-4桁+4桁)」
「時刻(N時-M時)」のパターンと重ならないことを確認する除外条件を追加する。
最小修正としては、`-`の直前直後が全角文字ではなく西暦らしい4桁+2桁+2桁の並びに
なっている場合(`\d{4}-\d{1,2}-\d{1,2}`)や、電話番号らしい`\d{2,4}-\d{4}-\d{4}`
パターンに一致する場合は`_GENERIC_EXPR`のマッチ候補から除外するのが良い。
より安全なのは、引く演算だけ「1個の演算子」に限定せず、`合計`/`いくら`/`お釣り`
と同様に、**明示的な「引く」「マイナス」等の日本語演算語がある場合のみ**
`-`記号なしの減算を許可し、`-`記号そのものは無条件では使わない(算用数字の式
`7-3=?`のような明示的な数式でのみ許可、かつ前後が数字N桁の羅列パターンに
一致しないことを確認)という方向。

### 1-B. 「合計」「いくら」という単語が文中にあるだけで文脈を無視して合計を計算する

`wants_total`の判定が単純な部分文字列マッチ(`"合計" in text` / `"いくら" in text`)
のため、否定文や、無関係な意味の同音異義語にも反応する。

| 入力 | 返り値 | 問題 |
|---|---|---|
| `1000円のセーターと500円のマフラーがあるけど、合計は聞いてないよ` | `1,000円 + 500円 = 1,500円です。合計1,500円になります。` | 「合計は聞いてない」という**否定**を無視して合計を計算してしまう |
| `いくら(salmon roe)が200円と300円で売っていた、どっちがいい?` | `200円 + 300円 = 500円です。合計500円になります。` | 「いくら」を「どのくらいの金額か」の意味だと誤認。実際は食べ物(イクラ)の名前で、ユーザーは2つの値段を**比較**したいだけなのに、無関係な合計を返す |

**重大度: 中〜高**。特に「いくら」の同音異義語(イクラ)は、日本語会話では普通に
出てくる語であり、金額の話と紛れて非常に紛らわしい誤答を生む。「合計は聞いてない」
のような否定文への無反応さも、電卓機能が「確実に正しく答える」ことを目的にしている
という設計意図(コード冒頭のコメント)に反する。

**修正案**: `wants_total`判定の直前に軽い否定チェックを入れる
(`合計|いくら`の前後15文字程度に`聞いてない|関係ない|の話じゃない|じゃなくて`
等が無いか確認する、简易ネガトゥ)。「いくら」誤爆は、直後に「円」を伴わない
場合や、直前に「の」が付く「イクラの」のような名詞用法を除外するなど。
完全な解決は困難だが、少なくとも「いくらが/いくらを/いくらは」+助詞のような
名詞的用法パターンを除外条件に加えると誤爆率は下がる。

### 1-C. 複数商品+お釣り/複数個購入+お釣りで、金額を静かに取りこぼす(最重要)

`try_calculate`の「お釣り」ロジックは**検出した円の値のうち最初と最後だけ**を
使う(`price, pay = yen_values[0], yen_values[-1]`)。3つ以上の金額が出てくる
複数商品購入のシナリオでは、中間の商品の値段を無視して静かに間違った額を返す。

| 入力 | 返り値 | 正しい答え | 問題 |
|---|---|---|---|
| `500円のお菓子と300円のジュースを買って1000円払ったらお釣りは?` | `1,000円 - 500円 = 500円です。お釣りは500円になります。` | 1000-(500+300)=**200円** | 300円のジュースの値段を完全に無視。**自信満々に間違った金額を返す** |
| `3000円のシャツを2枚買って、5000円払いました。お釣りは?` | `5,000円 - 3,000円 = 2,000円です。お釣りは2,000円になります。` | 3000×2=6000円必要なので、5000円では足りない(お釣りではなく不足) | 「2枚」という個数を無視し、単価だけで計算。実際は支払い不足のケースなのに、平然と「お釣り2,000円」と答える |

**重大度: 最高**。このモジュールは「日常のお金の計算を確実に正しく答える」ことが
存在意義(コード冒頭のコメントに明記)であり、まさにその中核シナリオ(複数商品
purchase + お釣り、複数個購入 + お釣り)で**静かに、確信を持って誤った金額**を
出す。ハルシネーションを防ぐために作られた機能が、逆にハルシネーションより
始末が悪い「規則ベースの誤答」を生んでいる。

**修正案**: お釣り計算では、最後の金額を「支払い額」とみなすのは良いが、
それ以外の**すべての**円の値(および個数×単価がある場合はその積)を合計して
「price」を再構成すべき。具体的には:
```python
if wants_change and len(yen_values) >= 2:
    pay = yen_values[-1]
    item_prices = yen_values[:-1]
    if count_value is not None and len(item_prices) == 1:
        price = item_prices[0] * count_value
    else:
        price = sum(item_prices)
    ...
```
また支払い額が総額より少ない場合は「お釣り」ではなく「不足」であることを
明示する分岐を追加すべき(現状は`pay <= price`で単に`None`を返し、モデルに
丸投げしてしまうため、不足という重要な情報が失われる)。

### 1-D. 小数の値段が「整数部の末尾1桁」に化ける(静かな誤答)

`_NUM_UNIT`正規表現`(\d[\d,]*)\s*(円|個|本|枚|つ|冊|杯|匹)`は小数点`.`を
扱えない。「150.5円」のような表記では、`150`にはマッチせず(直後が`.`で
単位でも空白でもないため)、代わりに`.`の後ろの`5円`にマッチしてしまう。

| 入力 | 返り値 | 正しい答え | 問題 |
|---|---|---|---|
| `1つ150.5円のお菓子を2個買ったら合計は?` | `5円 × 2 = 10円です。合計10円になります。` | 150.5×2=**301円** | `150.5`の`5`だけを値段として抽出し、合計を10円と自信満々に誤答 |

**重大度: 高**。小数の値段は現実には稀だが(消費税前価格など)、発生した場合に
`None`で安全にフォールバックするのではなく**明確に間違った数値**を出す点が
1-Cと同種の「静かな誤答」問題。

**修正案**: `_NUM_UNIT`の数値部分を`(\d[\d,]*(?:\.\d+)?)`に変更し、小数を
含む数値全体を1つの数として抽出できるようにする。`_to_int`も小数対応にする
(あるいは小数が出た場合は安全に`None`へフォールバックする方が「確実性」の
観点ではむしろ望ましいかもしれない)。

### 1-E. カウンター単位の抜け(false negative)

要求された「枚/杯/台/匹/箱」のうち、`台`と`箱`が`_NUM_UNIT`の単位リストに
**含まれていない**(現在: 円|個|本|枚|つ|冊|杯|匹)。また「1万円」のような
「万」表記の数値も認識できない(`\d[\d,]*`は漢数字単位を扱わない)。

| 入力 | 返り値 |
|---|---|
| `りんごを3箱買いました、1箱200円です、合計は?` | `None` |
| `自動車を1台500万円で買ったら合計いくら?` | `None` |
| `1万円のセーターと2000円のマフラーの合計は?` | `None` |

**重大度: 中**(誤答ではなく取りこぼしなので1-C/1-Dより実害は小さい。安全に
`None`へフォールバックしてモデルに委ねている点は良い挙動)。

**修正案**: `_NUM_UNIT`の単位一覧に`台`と`箱`を追加。「万」表記は
別途`(\d[\d,]*)\s*万\s*円`のようなパターンを追加して`* 10000`する処理を
入れると良い。

### 1-F. 支払い→値段の語順(価格が後に出てくる)でお釣りが計算されない

| 入力 | 返り値 |
|---|---|
| `1000円出して300円の物を買うとお釣りは?` | `None` |

`price, pay = yen_values[0], yen_values[-1]`という実装は、テキスト中に
「値段→支払い額」の順で書かれていることを前提にしている。この例は
「支払い額→値段」の順なので、`price=1000, pay=300`となり`pay > price`が
成立せず、`None`を返す。安全側に落ちてはいるが、自然な日本語表現の一部を
取りこぼしている。

**重大度: 中**(誤答はしないが取りこぼす)。**修正案**: 2値のうち大きい方を
支払い額、小さい方を価格とみなす(`max`/`min`を使う)ほうが語順に依存しない。

## 2. `try_datetime`に質問フィルタが無いことによる誤爆

`try_weather`/`try_holiday`/`try_knowledge`はいずれも`_looks_like_question()`
で「発言」と「質問」を区別しているが、**`try_datetime`だけこのチェックが無い**。
正規表現がテキスト中に現れるだけで無条件に発火する。

| 入力 | 返り値 | 問題 |
|---|---|---|
| `今何時か知らないけど、遅刻した` | `今は2時15分です。` | 単なる状況説明(過去のある時点で時刻を知らなかった)に、現在時刻を割り込ませる |
| `そのドラマ、今何時から?` | `今は2時15分です。` | ユーザーは**番組の開始時刻**を聞いているのに、無関係な現在時刻を返す。意味的にズレた回答 |
| `今何時だと思う?当てて` | `今は2時15分です。` | ユーザーがLilasに時刻を**当てさせる**クイズをしているのに、即座に正解を教えてしまい会話の趣旨を壊す |

**重大度: 中〜高**。特に「そのドラマ、今何時から?」のような「今+何時」を含むが
現在時刻の話ではないパターンは、日常会話で頻出しうる言い回しであり、意味的に
的外れな回答を自信満々に返す点で厄介。

**修正案**: `try_weather`等と同様に`_looks_like_question`でのフィルタを追加する
ことに加え、「今何時」の直後に「から」「まで」等が続く場合(=何かの開始/終了
時刻を聞いている)は除外する軽いネガティブルックアヘッドを追加する:
```python
if re.search(r"今.{0,3}何時", text) and not re.search(r"今.{0,3}何時\s*(から|まで|に|の)", text):
```

## 3. 電卓と知識/天気/日付ツールが同一メッセージ内で競合し、片方が完全に無視される

`chat.py`が`try_calculate`→`try_tools`の順で**最初に非Noneを返した1件のみ**を
採用する設計のため、1メッセージに2つの話題(計算+知識/天気/時刻など)が混在
すると、後者が黙って無視される。

| 入力 | 返り値 | 問題 |
|---|---|---|
| `今日の天気を教えて、あと5+3は?` | `5 + 3 = 8です。`(天気は完全に無視) | 天気の質問が握りつぶされる |
| `富士山の高さは?あと100+50は?` | `100 + 50 = 150です。`(富士山の質問は完全に無視) | 知識質問が握りつぶされる |
| `100円と200円のお菓子、合計いくら?ところで今何時?` | `100円 + 200円 = 300円です。合計300円になります。`(時刻の質問は無視) | 時刻質問が握りつぶされる |

**重大度: 中**(単一トピックの会話がほとんどであれば影響は限定的だが、複合質問は
自然な会話でよくあるパターンであり、片方の質問が完全に無回答になるのはユーザー
体験として目立つ)。

**修正案**: 根本対応は「複数の事実を1ターンで拾って両方をプロンプトに注入する」
仕組みに変更すること(`try_calculate`と`try_tools`両方を試し、両方Noneでなければ
両方の事実文字列を連結してプロンプトに渡す)。最小対応としては、少なくとも
`try_calculate`が発火した場合でも`try_tools`を追加で呼び、両方の結果を結合する
ようにするだけでも改善する。

## 4. 二人称代名詞の自己言及リストの漏れ(既存バグと同種の再発)

`_SELF_REFERENCE_WORDS = {"あなた", "あなたさま", "君", "きみ", "そちら", "お前", "あんた"}`
に対して、タスクで指定された追加バリエーションをテストした結果、複数の語が
**リストから漏れている**ことを確認した(`_extract_search_query`が`None`ではない
= 除外されずWikipedia検索に進んでしまう)。

| 入力 | `_extract_search_query()`の返り値 | 判定 |
|---|---|---|
| `あなたは誰?` | `None` | 正しく除外(既存の修正が機能) |
| `あなたさまは誰ですか?` | `None` | 正しく除外 |
| `そちらは誰?` / `お前は誰?` / `あんたは誰?` | いずれも`None` | 正しく除外 |
| `てめえは誰だ` | `('てめえ', 'who', None)` | **漏れ**。「てめえ」(=お前の俗な言い方)を検索クエリとして扱ってしまう |
| `貴殿は誰か` | `('貴殿', 'who', None)` | **漏れ**。「貴殿」(=二人称の敬語)も同様 |
| `あなた様は誰ですか?` | `('あなた様', 'who', None)` | **漏れ**。漢字の「様」表記(`あなたさま`という**かな**表記のみ登録されていた)。既に修正済みの元バグ(#2)と全く同種の再発パターン |
| `お前さんは誰?` | `('お前さん', 'who', None)` | **漏れ**。「お前さん」も「お前」の変化形として未登録 |

**重大度: 中〜高**(「あなた様」表記の漏れは、修正済みだったはずのバグ#2と
本質的に同じ不具合が別表記で残っている点で特に問題)。実際にWikipedia検索まで
進んだ場合、「てめえ」「貴殿」は代名詞の語源記事や無関係な項目がヒットする
可能性があり、元のバグ#2と同じ症状(自分が誰かと聞かれて無関係なWikipedia
記事を読み上げる)を再現しうる。

**修正案**: 完全な列挙ではなく、パターンマッチに変更するのが保守性の観点で
望ましい。例えば「様/さま」「さん」等の敬称サフィックスを剥がした上でベース
の代名詞と比較する:
```python
_SELF_REFERENCE_BASE = {"あなた", "君", "きみ", "そちら", "お前", "あんた", "てめえ", "貴殿", "貴様"}
_HONORIFIC_SUFFIX = re.compile(r"(様|さま|さん)$")
def _is_self_reference(q: str) -> bool:
    return _HONORIFIC_SUFFIX.sub("", q) in _SELF_REFERENCE_BASE or q in _SELF_REFERENCE_BASE
```

## 5. 反語・修辞的疑問文が疑問符付きだと誤爆する

`_looks_like_question`は文末の疑問符や「教えて」等の疑問マーカーの有無だけを
見ているため、実際には「誰」「どこ」という疑問詞が使われていても、Lilas自身
への質問ではない文(慣用表現・反語)が疑問符付きだと誤爆する。

| 入力 | `_extract_search_query()` | 問題 |
|---|---|---|
| `誰か来るかどうかは誰にも分からないよね?` | `('誰か来るかどうか', 'who', None)` | 「誰にも分からない」という慣用句を"who is 誰か来るかどうか"という質問だと誤認し、Wikipedia検索に進んでしまう |
| `ここはどこか分からないよ、教えて` | `('ここ', 'where', ...)` | 「ここはどこか分からない」を"where is ここ"と誤認。「ここ」でWikipedia検索してしまう |

疑問符が無いバリエーション(`誰か来るかどうかは誰にも分からない` / `ここはどこか
分からない`)は`_looks_like_question`が`False`を返すため無事だが、文末に`?`や
「教えて」を付けた自然な言い方(「〜だよね?」「教えて」)は普通に発生しうる。

**重大度: 中**。実際にWikipedia検索まで進んでも「誰か来るかどうか」や「ここ」
というクエリはヒットしないかヒットしても無関係な記事の可能性が高く、致命的な
誤答にはなりにくいが、無駄なAPI呼び出しと、稀に的外れな「Wikipediaで調べたところ...」
という返答を生むリスクがある。

**修正案**: 「は誰にも」「はどこにも」のように、疑問詞の直後に「にも」が続く
場合は否定/強調構文(「誰にも分からない」「どこにも無い」)である可能性が高い
ので除外するネガティブルックアヘッドを追加する。

## 6. 知識トリガーのパターン網羅漏れ(false negative、広範囲)

`_KNOWLEDGE_TRIGGERS`には「の高さ」「の人口」「って何」「とは」「は誰」
「って誰」「はどこ」「の意味」しか登録されていない。以下は**すべて`None`**
(トリガーせず、モデル生成に丸投げされる)ことを確認した。

| 入力 | `extract_q` |
|---|---|
| `日本の首都は?` | `None` |
| `日本の国旗はどんな色?` | `None` |
| `日本の通貨は何?` / `日本の通貨は何ですか?` | `None` |
| `東京から大阪までの距離は?` | `None` |
| `このリンゴの値段はいくら?` | `None` |
| `織田信長はいつ死んだ?` | `None` |
| `京都は何県?` | `None` |
| `猫は何ですか?` | `None`(「猫って何?」は`って何`パターンでヒットするが、「猫は何ですか?」という**より一般的な丁寧語の言い回し**はヒットしない) |

一方、`北海道はどこの国?`は偶然`はどこ`パターンにヒットして`('北海道', 'where', ...)`
を返す(「どこの国」という意図とは無関係に、たまたま「はどこ」という部分文字列
一致で捕まっただけ)。

**重大度: 中(だが範囲が広い)**。特に「Xは何ですか?」という**最も標準的な
丁寧語の疑問文**が「って何」「とは」という限定パターンでしか捕まらず取りこぼす
点は、実運用でのヒット率に大きく影響しうる。「の首都/の国旗/の通貨/の距離/
の値段/いつ/どこの国/何県」は個々のジャンルとしては相対的にニッチだが、
合計すると相当な割合の一般知識質問を取りこぼす。

**修正案**:
- 汎用の`(.+?)は(?:何|なに)(?:です)?[?？]`パターンを追加(「とは」と重複しない
  ようにするか、「とは」パターンより後ろに置いて丁寧語版のみ拾う)。
- `の首都/の国旗/の通貨`は`(.+?)の(首都|国旗|国歌|通貨)`のような複合パターンで
  まとめて追加できる。
- `いつ`は`(.+?)はいつ`、`何県`は`(.+?)は何県`のように、既存の`はどこ`と同型の
  シンプルなパターンを追加すれば良い。

## パターンのまとめ (優先度順)

深刻度の高い順に並べる。「静かに確信を持って間違った数値を返す」系(1-C, 1-D)
は、この電卓機能の存在意義(ハルシネーション防止)を直接損なうため最優先。

### severity: breaks conversation badly(会話を大きく壊す/信頼を損なう静かな誤答)

1. **【1-C】複数商品購入時のお釣り計算が中間の商品の値段を無視する**
   `500円のお菓子と300円のジュースを買って1000円払ったらお釣りは?` →
   誤って`500円`(正しくは200円)。複数個購入(`3000円のシャツを2枚`)でも
   個数を無視して誤答。
   修正: `price = sum(yen_values[:-1])`(または個数×単価)に変更。

2. **【1-A】日付・電話番号・郵便番号・時間範囲の「N-M」表記を減算と誤認**
   `2026-09-10ですか?` → `2,026 - 9 = 2,017です。`。日付質問が
   `try_datetime`に届く前に電卓が横取りしてしまう。電話番号は負の数
   `-1,144`という露骨に不自然な「答え」を返す。
   修正: `-`演算子のマッチに、日付/電話番号/郵便番号らしい数字パターンの
   除外条件を追加。

3. **【1-D】小数の値段が末尾1桁だけの数値として誤抽出される**
   `1つ150.5円のお菓子を2個買ったら合計は?` → `5円 × 2 = 10円`
   (正しくは301円)。
   修正: `_NUM_UNIT`の数値部分に`(?:\.\d+)?`を許可。

### severity: minor annoyance(誤爆はするが実害は限定的、または取りこぼし)

4. **【4】自己言及の二人称代名詞リストの漏れ(既存バグ#2の再発パターン)**
   `てめえ`/`貴殿`/`あなた様`(漢字)/`お前さん`が`_SELF_REFERENCE_WORDS`に
   無く、Wikipedia検索に進んでしまう。特に`あなた様`は修正済みバグ#2と
   同種の再発。
   修正: 敬称サフィックス(様/さま/さん)を剥がして基本語と比較する方式に
   変更。

5. **【2】`try_datetime`に質問フィルタが無い**
   `そのドラマ、今何時から?`(番組の開始時刻を聞いている)にも
   無関係な現在時刻`今は2時15分です。`を返す。
   修正: `_looks_like_question`によるフィルタ追加+「今何時」直後の
   「から/まで」を除外。

6. **【1-B】「合計」「いくら」の部分文字列マッチが否定文・同音異義語に反応**
   `合計は聞いてないよ`でも合計を計算、「いくら」(イクラ)を金額の話と誤認。
   修正: 直前直後の軽い否定チェック、名詞用法の除外。

7. **【3】電卓と知識/天気/時刻ツールが競合し、後者が完全に無視される**
   複合質問(`天気を教えて、あと5+3は?`)で片方が握りつぶされる。
   修正: `try_calculate`と`try_tools`の結果を両方収集して連結する。

8. **【5】反語・慣用句が疑問符付きだと`は誰/はどこ`パターンに誤爆**
   `誰にも分からないよね?` → 「誰か来るかどうか」をクエリ化してしまう
   (実害は無駄なAPI呼び出し程度で軽微)。
   修正: 「にも」が続く場合を除外。

### severity: cosmetic(取りこぼしのみ、誤答はしない)

9. **【1-E】カウンター単位`台`/`箱`の未対応、「万」表記の未対応**
10. **【1-F】「支払い額→値段」の語順だとお釣りが計算されない(語順依存)**
11. **【6】知識トリガーの網羅漏れ**: `の首都/の国旗/の通貨/の距離/の値段/いつ/
    どこの国/何県`、および最も一般的な`Xは何ですか?`という丁寧語表現。
    件数は多いが、いずれも安全に`None`へフォールバックしてモデル生成に
    委ねるため、電卓の誤答系バグより実害は小さい。
