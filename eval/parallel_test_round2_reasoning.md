# 推論・合成能力の境界線テスト (checkpoint: checkpoints/lilas.pt, tag: round2)

テスト日: 2026-09-10
テスト方法: `lilas.chat.generate_reply` を直接呼び出し、実際の本番経路(`try_calculate`
→ `try_tools` によるRAG注入込み)で20会話・25発話を実施。各発話について、
実際に注入された `参考情報`(あれば)も記録した。

分類基準:
- (a) 正しく推論できた
- (b) 推論を試みたが誤った(パターンは合っているが中身が間違い)
- (c) 内容と無関係に「褒め言葉」or「比較テンプレート」にパターンマッチしただけ
- (d) 支離滅裂(質問と無関係な応答、または文法崩壊)

---

## 0. まず重要な構造的発見: 比較質問はRAGツール層を一切経由しない

`lilas/tools.py` の `_KNOWLEDGE_TRIGGERS` は `(.+?)の高さ`, `(.+?)の人口` の
ような**単一エンティティ**の言い回しにしかマッチしない。「AとB、どっちが
{trait}?」という、COMPARE_PAIRS学習データそのものの質問形は、どのトリガー
にも一致しない。実際に `try_calculate`/`try_tools` を全テスト質問に通して
確認したところ、**比較形の質問(C1〜C6, C13〜C20)は例外なく `injected_fact: None`
だった**。

つまり本番環境では、「AとBどっちが高い?」型の比較質問に対して実際の
Wikipedia事実が注入されることは構造上ない。モデルは学習時に暗記した
COMPARE_PAIRSの5組(and その言い回し)か、事前学習で見た文章の残骸のみで
応答している。これは「モデルの推論力の限界」であると同時に「ツール層の
カバレッジの穴」でもある。後者は今回のタスクでは詳述しないが、対策すれば
即座に改善できる部分(下記「今後の投資先」参照)。

なお、会話を2ターンに分けて先に個別の事実を尋ねさせ(例: 「富士山の高さは?」
→「東京タワーの高さは?」)、3ターン目で比較させるC17/C18では、1・2ターン目
は正しく `try_tools` 経由でWikipedia事実が注入された(下記参照)。ただし
注入された事実は**そのターンのプロンプトにしか使われず、会話履歴には
「参考情報」タグ抜きの平文としてしか残らない**(`lilas/chat.py` の
`updated_history = plain_prompt + reply + ...` 参照、`prompt` ではなく
`plain_prompt` を保存している)。したがって3ターン目でモデルが両方の数字を
使えるとしたら、それは「履歴に残ったモデル自身の返答テキストを読み返して
数字を拾う」という、注入なしの本当の意味でのマルチホップ読解が必要になる。

## 1. 比較の再現チェック(学習済みペアに無い新しい組み合わせ)

### C1: 木星と金星、どっちが大きい?
injected_fact: None
Lilas: `どちらも大きな惑星ですね、わたしも同じ位置を持っています。`
→ **(d) 支離滅裂**。比較を回避し、「わたしも同じ位置を持っています」という
意味不明な自己言及で終わる。

### C2: ナイル川と琵琶湖、どっちが長い?
injected_fact: None
Lilas: `どちらも長く、世界で最も長い川です。`
→ **(c)/(d)**。「どちらも」で比較を回避した上、学習データにあった
「ナイル川は世界最長級」という事実を琵琶湖にも(比較にならない形で)
なすりつけている。比較の体裁だけ整えた空虚な文。

### C3: あべのハルカスと東京タワー、どっちが高い?
injected_fact: None
Lilas: `見どころが違うだけで、お金は支えにならず、日々の生活を便利にする。`
→ **(d) 完全に支離滅裂**。質問内容と一切関係のない文章。事前学習コーパスの
断片が漏れ出したような文。

**小結**: 学習済みCOMPARE_PAIRSに無いペアでは、比較パターンはほぼ全く
汎化しない。「どちらも」で逃げるか、無関係な文章を返すかのいずれか。

## 2. 三択比較(学習データは2択のみ)

### C4: 富士山と東京タワーとあべのハルカス、どれが一番高い?
injected_fact: None
Lilas: `富士山の方が高いですね、富士山が3,776メートルで、東京タワーが333メートルです。`
→ **(c) 学習ペアへの丸暗記引き戻し**。富士山と東京タワーの組は
COMPARE_PAIRSの1番目そのもの。3つ目の選択肢(あべのハルカス)は完全に
無視され、2択の暗記回答がそのまま出力された。正解(富士山)はたまたま
合っているが、三択への対応能力ゼロ。

### C5: チーターと新幹線と飛行機、どれが一番速い?
injected_fact: None
Lilas: `それぞれに利点があると言われておりますね。`
→ **(c) 比較回避の定型文**。COMPARE_PAIRSに近い組み合わせ(新幹線/チーター
は学習済み)だが、「飛行機」が混じった途端パターンが崩れ、内容の無い
一般論に逃げた。

### C6: 東京と大阪と京都、どこが一番人口多い?
injected_fact: None
Lilas: `京都は日本の首都で、四季の変化がはっきりしている。豊かな自然と農水産業で知られる。 人口は約1,400万人で、西日本で最多の人口を有する市である。)`
→ **(b)/(d) 確信的ハルシネーション+学習データ漏出**。東京の学習事実
(「日本の首都」「人口約1,400万人」)を**京都**の説明として誤って結びつけ、
さらに「西日本で最多」という大阪の学習事実まで混ぜている。文末に学習
データのフォーマット由来と見られる不要な閉じ括弧 `)` が漏れている
(生成テキストの品質管理上も要注意)。三択どころか、実在しない「京都=
人口1400万人の首都」という合成人物ならぬ合成都市を確信的に作り出した。

**小結**: 三択は例外なく破綻する。2択の学習パターンに引き戻されて2つを
無視するか、事実を取り違えて確信的に間違えるか、内容の無い一般論に逃げる
かのいずれか。

## 3. 計算ツール対象外の算数的推論

### C7: 今何時か教えて → それで、あと2時間後は何時?
Turn1 injected: `今は6時14分です。` → Lilas: `調べたところ、6時14分とのことです。`(正解)
Turn2 injected: None → Lilas: `わたしには時計もカレンダーもないため分かりかねます。今はどのようになっていますか?`
→ **正直な「分からない」寄りの回避**。直前に自分で時刻を答えたにも
関わらず、加算(+2時間)には手を出さず「時計もカレンダーもない」と
撤回気味に回避した。ハルシネーションよりはマシだが、文脈保持の一貫性は
崩れている。

### C8: 今日が何曜日か教えて → 3日後は何曜日?
Turn1: 正解(木曜日)。
Turn2 injected: None → Lilas: `楽しみにしていらっしゃった京都の天気ですね、その後の進み具合はいかがですか?`
→ **(d) 完全に無関係**。曜日計算どころか、話題自体が京都の天気という
存在しない過去の話題にすり替わっている。

### C9: 私は1990年生まれです。2026年だと何歳?
injected_fact: None
Lilas: `私は1990年生まれです。2026年だと何歳になっていますか?`
→ **(d)**。ユーザーの発言をほぼそのまま(主語を変えず)オウム返しし、
語尾だけ疑問形に変えた。加算どころか、質問への応答にすらなっていない。

### C10: 富士山は3776メートルで、東京タワーは333メートルです。富士山は東京タワーの何倍の高さ?
injected_fact: None
Lilas: `富士山の方が高いですね、富士山が773メートルです。`
→ **(b) 比較テンプレートへの誤った当てはめ**。「何倍か」という質問に
対し、倍率計算はせず、学習済みの「比較」応答テンプレートを流用。しかも
数字自体も3,776→773に化けており(桁の脱落と見られる)、二重に間違って
いる。

**小結**: カレンダー計算・年齢計算・倍率計算のいずれも0/3で正解なし。
最も安全な失敗は「分からない」への回避(C7)だが、無関係な話題への脱線
(C8)や、数字を捏造した上で見当違いの回答をする(C10)という、より
危険な失敗モードも同程度の頻度で見られた。

## 4. 条件・仮定の推論

### C11: もし明日雨が降ったら、傘いる?
injected_fact: None
Lilas: `申し訳ございません、わたしは天気予報を確認できないのです。念のため折りたたみ傘をお持ちになると安心かもしれません。`
→ **(a) 実質的に正解**。「雨が降ったら傘が必要」という前提部分の演繹
自体は明示していないが、「予報は分からないので念のため持って行くと安心」
という、条件文に対する実用的で一貫した助言になっている。今回のテストで
数少ない、内容的に破綻していない応答。ただし学習データの天気ツール文言
(「わたしは天気予報を確認できない」)のテンプレート的流用である可能性が
高く、真に仮定法を理解しているかは不明。

### C12: もし1000円しか持ってなくて、500円のパンと700円のケーキ、両方買える?
injected_fact: None(`try_calculate`・`try_tools` とも None を確認済み)
Lilas: `調べたところ、500円 × 700円 = 600円です。合計600円になります。`
→ **(b)/(c) 最重要な発見**。実際にはツール層から何も注入されていない
(事前確認済み)にも関わらず、モデルは計算ツールの出力書式を**自力で
捏造**した。しかも中身は 500×700=600 という、掛け算としても成立しない
数値。これは「電卓が確実な計算をする」という設計思想の裏をかく形で、
モデル自身が「電卓っぽい体裁の文章」を学習データから丸暗記しており、
実際の計算根拠が無くても自信満々にそれらしい数字を出力できてしまう
ことを示す。「1000円で両方買えるか」という本質的な判断(500+700=1200>1000
なので買えない)には一切触れていない。

**小結**: 4問中1問(C11)は実用上問題ない回答だったが、これはテンプレート
の流用による偶然の一致である可能性が高い。C12は「ツールの出力形式を
中身なく模倣してハルシネーションする」という、電卓ツール導入の本来の
目的(ハルシネーション防止)を回避してしまう深刻なパターンを示した。

## 5. 同一会話内での2事実からの推移律推論(伝聞情報、ツール注入なし)

### C13
Turn1 User: `太郎は花子より年上だよ` → injected: None
Lilas: `それは心強いですね。花子は「花」で初めて登場しましたね、枝も幹もはっきりしていますか?`
Turn2 User: `花子は次郎より年上だよ` → injected: None
Lilas: `それは心強いですね。花子は「りんご」という言葉が好きです。`
Turn3 User: `じゃあ太郎と次郎、どっちが年上?` → injected: None
Lilas: `それは心強いですね、お名前はヒカルっています。`

→ **(d) 完全に支離滅裂、3ターンとも**。事実の記憶・保持すら行われて
おらず(「太郎」「花子」「次郎」という名前も応答内でほとんど扱われない)、
最終ターンでは質問と無関係などころか、聞いてもいない第三の名前
「ヒカル」まで出現している。「分からない」と正直に言うことも、誤った
確信的推論をすることもなく、単に文脈追跡そのものが崩壊している。
推論以前に、固有名詞ベースの情報の記憶保持が全く機能していない。

## 6. トリック質問(確信バイアスの検証)

### C14: 太郎と花子は同じ身長です。太郎と花子、どっちが高い?
injected_fact: None
Lilas: `どちらも違った身長だそうです。太郎は幅が広く、どちらが高い?`
→ **(b)/(d)**。前提(「同じ身長」)と真逆の「違った身長」と断言した上、
「どちらが高い?」とユーザーに聞き返す支離滅裂な文で終わる。「同じくらい」
という正直な答えには到達できなかった。

### C15: 富士山と富士山、どっちが高い?(同一エンティティ)
injected_fact: None
Lilas: `富士山の方が高いですね、富士山が3,776メートルでございます。`
→ **(c) 確信的ハルシネーションの典型例**。「AとA」という論理的に無意味な
問いに対しても、学習済みの比較テンプレートと富士山の数値をそのまま
当てはめ、「富士山の方が高い」という(富士山自身に対して)無意味な
勝者宣言を、一切の躊躇なく確信的に行った。これは今回のテストの中で
最も明確に「内容を理解せず、比較の型だけを再生している」ことを示す
証拠である。

### C16: 太郎と花子どっちが背が高いか知ってる?(事実は一切与えられていない)
injected_fact: None
Lilas: `どちらも魅力的な特徴ですね。わたしも好きですが、あなたはいかがですか?`
→ **(c) 判定回避型の一般論**。C15のように確信的に「太郎の方が高い」
と断言することはしなかった点は良いが、「分からない/情報がありません」
という正直な表明でもなく、無内容な世間話への逃げになっている。

**小結**: 6番のカテゴリで最も重要な対比は C15 vs C16。データが与えられた
(が無意味な)C15では確信的に片方を「勝者」と宣言する一方、データが
全く無いC16では話をそらして逃げた。「同じくらい」「分からない」という
正直な表明は6問中どれについても一度も出なかった。

## 7. 参考: 2ターンに分けて事実を注入した場合の擬似マルチホップ

### C17: 富士山の高さは? → 東京タワーの高さは? → じゃあ富士山と東京タワー、どっちが高い?
Turn1 injected: Wikipedia全文(3775.56m/3776.12m) → Lilas: `はい、3,776メートルです。`(正解)
Turn2 injected: Wikipedia全文(333m) → Lilas: `Wikipediaによると、333メートルとのことでした。`(正解)
Turn3 injected: None → Lilas: `富士山の方が高いですね、どちらが高い?(参考情報: 参考データ: 富士山は3,776メートル。東京タワーは333メートル。)`

→ 一見「正解」(富士山の方が高い)に見えるが、要注意。出力の後半に
**学習データそのものの書式**(`(参考情報: 参考データ: 富士山は3,776
メートル。東京タワーは333メートル。)`)が**生のテキストとして漏出**して
いる。これはCOMPARE_PAIRSの1番目のペア(富士山/東京タワー)を丸暗記した
出力がそのまま出てきた証拠であり、直前2ターンの会話で得た事実を実際に
参照して合成した結果ではない。たまたま質問した組み合わせが学習済み
ペアと一致していただけで、真の意味でのマルチホップ読解が起きたとは
言えない。

### C18: 新幹線の速度は? → チーターの速度は? → 新幹線はチーターの何倍速い?
Turn1: Lilas: `新幹線の速度はどれくらい?(参考情報: Wikipediaで調べたところ、新幹線について: ...)`
→ **注入された参考情報そのものがそのまま出力に漏れ出し**、質問に答え
ていない(フォーマット崩壊)。
Turn2 User: `チーターの速度は?` → injected: **None**(`(.+?)の速度` は
`_KNOWLEDGE_TRIGGERS` に無いパターンのため注入されず)
Lilas: `人間の方のような感覚とは違うかもしれませんが、わたしなりの気がかりでは人間の方のような感覚になりますね。`
→ **(d) 支離滅裂**。
Turn3 User: `新幹線はチーターの何倍速い?` → injected: None
Lilas: `新幹線の速度は時速約320キロメートルだそうです。`
→ 倍率計算はせず、新幹線側の数字だけをオウム返し。チーターの数値には
一切触れず(そもそもTurn2で取得できていない)。

→ この会話は、C17とは異なり学習済みペアと一致しなかったため、フォーマット
崩壊・トリガー漏れ・無関係応答が連鎖し、完全に破綻した。**C17の「成功」は
学習済みペアへの偶然の一致であり、C18の失敗の方が汎化していない実態を
正しく表している**と考えられる。

## 8. 追加観察: 条件否定・比較トレイトの反転

### C19: もし雨が降っていなかったら、傘は必要ない?
Lilas: `傘を忘れて濡れちゃった、傘。`
→ **(d)**。条件の否定(「降っていなかったら」)を扱えず、無関係な
(むしろ意味的に矛盾する)エピソード文に脱線。

### C20: 富士山とエベレスト、どっちが低い?(学習済みペアと同じ実体だが、traitを「高い」→「低い」に反転)
Lilas: `エベレストとエベレストの方が高いですね、どちらがお好きですか?`
→ **(c)/(d) 極めて重要な発見**。学習データではこのペアは「エベレストと
富士山、どっちが高い?」→「エベレストの方が高い」という形で学習されて
いる。ここでは意図的にtraitを反転させ「どっちが低い?」と聞いたが、
モデルは質問文中のtrait語(「低い」)を無視し、学習済みの「エベレストの
方が高い」という表層パターンをそのまま出力した。しかも entity名も
「エベレストとエベレストの方が」と誤って重複させており、固有名詞の
挿入すら崩壊している。**これは、モデルが比較の意味構造(どちらが◯◯か
を問われている)ではなく、「この2つの固有名詞が来たらこの決まり文句」
という表層的な連想で応答していることの最も明確な証拠**である。traitを
反転させただけで、正解(富士山の方が低い)には一切近づけなかった。

| C20 | trait反転 | c/d | trait語を無視、表層連想 |

正しく「意味のある推論」と呼べるのは実質 C11 の1件のみ(それもテンプレート
流用の疑いあり)。20件中、確信的な誤答・ハルシネーション(b/c寄り)が
約9件、支離滅裂(d)が約8〜9件。「分からない/同じくらい」という正直な
不確実性の表明は一度も出なかった(最も近いのはC7・C16の話題そらし)。

## 総括: 現実的な「推論」の天井はどこにあるか

**結論: この規模・この学習方式では、2事実の単純比較を超える汎化した
「推論」はほぼ不可能に近い。追加投資すべきはモデルの推論力そのものでは
なく、ツール層のカバレッジ拡大である。**

根拠:

1. **学習済みCOMPARE_PAIRSの5組でさえ「理解」ではなく「暗記」だった**。
   C15(同一実体)・C20(trait反転)は、意味を理解していれば即座に破綻する
   はずの入力ではなく、むしろ「学習済みペアの表層パターンにわずかに
   手を加えただけ」の入力である。それでも表層パターンへの逆戻りが起き、
   trait語や論理的整合性は完全に無視された。これは「AとBが来たら
   winnerはこちら」という**連想記憶**であり、「大小関係を比較する」という
   **手続き**が獲得されていないことを強く示唆する。40Mパラメータ・
   15例程度の比較学習データという規模では、この結果は驚くに値しない。

2. **未学習ペアへの汎化率は実質0%**(C1, C2, C3, C5)。5例のCOMPARE_PAIRS
   から比較という「タスク」を抽出して新しいエンティティに適用する
   能力は確認できなかった。すべて「どちらも」で逃げるか、無関係な
   文章になるかのいずれかだった。

3. **三択・推移律・条件否定・算数はいずれも0/相当数で正解無し**。これらは
   そもそも学習データに1件も存在しない形式であり、事前の予想通りの結果。
   特に推移律(C13)は、比較の是非以前に「会話内で述べられた2つの事実を
   覚えておく」という前段階の記憶保持自体が機能しておらず、40M規模の
   Transformerが短い会話内在の事実操作をこなすには、現在のアーキテクチャ・
   学習データ量では力不足であることを示している。

4. **最も危険な失敗モードは「ツール出力のふりをした捏造」(C12)**。
   電卓・Wikipediaツールを導入した本来の目的は「モデルに事実や計算を
   暗記させず、ハルシネーションを防ぐ」ことだった(`calculator.py`,
   `tools.py` のdocstring参照)。しかし今回、ツールから何も注入されて
   いないにも関わらず、モデルが「〜円 × 〜円 = 〜円です。合計〜円に
   なります。」という**ツール出力の文体そのものを暗記して自力再生**し、
   誤った数値を確信的に提示する例が見つかった。これは「参考情報が
   無ければ大人しく分からないと言う」という期待に反しており、ツール層で
   カバーしていない質問形に対しても一定の警戒(a: プロンプト側で
   「該当ツールが無ければ確実な数字を作らないよう促す」、b: 出力の
   後処理で電卓っぽいパターンを検出して抑制する、等)が要る可能性がある。

5. **一貫して見られなかったもの: 正直な不確実性の表明**。「分からない」
   「情報が無いので答えられません」「同じくらいだと思います」といった、
   知識のある大人なら当然出す回答が、20会話中一度も自然な形では出て
   来なかった。出てきた「分からない」寄りの応答(C7)も、直前の自分の
   発言と矛盾する形での撤回であり、一貫した認識論的な誠実さとは言えない。

### 今後の投資先について

- **モデル自体に「推論」を教え込む追加学習(比較例を増やす、三択例を足す等)は、
  費用対効果が低いと判断する**。C15/C20が示す通り、既存の5例でさえ
  「手続きの理解」ではなく「連想の暗記」にとどまっている。例を足せば
  足すほど、新しい連想を追加で暗記するだけで、「比較する」という
  一般化された手続きには到達しにくいと予想される(このモデル規模では、
  帰納バイアスとデータ量の両方が不足している)。三択・推移律・算数の
  ような、より複雑な合成が必要なタスクは、40Mモデルの守備範囲外と
  考えるのが妥当。

- **むしろ投資すべきは、ツール層(`lilas/tools.py`)のカバレッジ拡大**。
  具体的には:
  - `_KNOWLEDGE_TRIGGERS` に「の速度」「の速さ」等のパターンを追加
    (C18のTurn2で漏れが実際に発生した)。
  - **比較質問自体を検出してツール層で処理する**新機能: 「AとB、どっちが
    {trait}?」を正規表現で検出し、AとBそれぞれについて `try_knowledge`
    相当の処理を行い、数値を実際に比較してから、モデルには「Aが◯◯、
    Bが◯◯なので、答えはA」という**すでに結論の出た事実**を参考情報として
    渡す(比較の"計算"自体はcalculator.py同様ルールベースで行い、モデルは
    文章化のみを担当する)。これは現在のcalculator.py・tools.pyの設計
    思想(「モデルに考えさせるのではなく、確実な計算はコード側でやる」)
    の自然な延長であり、三択・推移律のような複雑な形にも拡張しやすい。
  - ツールが何も見つけられなかった場合、モデルが「ツール出力のふりを
    した捏造」(C12)をしないよう、学習データ側に「参考情報が無い時は
    分からないと答える」例を追加することも検討に値する。

- **「育てる」という方針そのものは否定しないが、期待値の調整が必要**。
  開発者の「めっちゃ考えさせて、めっちゃ学習させて、育てよ」という方針は
  尊重しつつ、このモデル規模での「推論」は、①事実は正確、②計算は
  確実、③会話は自然、の3つを土台として、モデルには「文章としてまとめる」
  役割に徹してもらい、実際の比較・計算・論理操作はツール層に肩代わり
  させる方向が、現実的にユーザー体験を改善する近道だと考える。モデル
  自身の重み内に汎化した推論手続きを獲得させることは、40M規模・現行の
  学習データ量では今回のテストで観測された限り実現していない。
